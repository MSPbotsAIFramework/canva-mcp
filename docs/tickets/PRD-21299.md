## Product design

### Goals / Non-goals

**Goals (v1, this ticket):**
- Give an Agent-platform tenant that has connected their Canva account, via an MCP-compatible AI (Claude, ChatGPT, Cursor, or any other MCP client behind the platform's gateway), the ability to: see who they are connected as, browse/search their Canva designs, read a design's metadata, create a new blank/typed design, export an existing design to a common file format and retrieve the download link, upload an externally-hosted image/video as a new Canva asset, read an asset's metadata, and list the contents of a Canva folder (including the root Projects folder and the Uploads folder).
- Ship a connector that follows the vendor-mcp-development SOP's non-functional contract: Streamable HTTP, stateless, Header-only credentials, request-level isolation, structured errors, `/health`.

**Non-goals (v1, explicitly out of scope — not because they are hard, but because the ticket does not ask for them and the SOP caps tool count / scope creep):**
- Design *content* editing (adding/moving/styling elements inside a design) — Canva's Connect API does not expose element-level editing at all; Canva's own editor is the only way to edit design content, so this is not a v1-vs-v2 choice, it is not possible via this API today.
- Comments, Autofill (brand-template autofill), Brand Templates, Analytics, Design Import, Resizes, Merges, Generations (AI image/design generation), Image Transformations, Print Partner designs — all real Canva Connect API resource groups, none requested by the ticket. Listed here so a future ticket can point at a specific gap instead of re-discovering the full API surface.
- Direct binary asset upload (sending raw file bytes to the MCP tool). v1 only supports "upload from a URL" (`POST /v1/assets/upload-url` style job) because MCP tool arguments are JSON — accepting inline binary content would mean base64-encoding arbitrarily large files into a single tool call, which conflicts with the SOP's token-economy rules (§A4: responses capped, no unbounded payloads) and isn't needed for an AI-assistant use case (the agent virtually always has a URL, not raw bytes, to hand over).
- Deleting or updating existing designs/assets. The SOP defaults every tool to read-only and requires a stated business need for write/destructive tools with unambiguous resource IDs; the ticket does not ask for deletion, and an AI agent silently deleting a user's Canva content is exactly the "ambiguous batch delete" pattern the SOP tells us to avoid by not building until asked.
- Implementing Canva's OAuth authorization/consent/refresh flow inside this MCP service. See "Decisions made by DEV01" below.

### Acceptance criteria

- **AC1**: Given a tenant has a valid Canva access token configured for this connector, When the agent calls `tools/list` through the gateway, Then the canva-mcp tools are returned (see Tech design §4 for the exact list) and each tool's description is ≤500 characters with a ≤100-character first line (SOP §A4 token-economy rule).
- **AC2**: Given no `X-Canva-Access-Token` header is sent, When any Canva tool is called, Then the service returns HTTP 401 with a body naming the missing header — not HTTP 500 and not a Canva-shaped error.
- **AC3**: Given a valid access token, When `canva_list_designs` is called with no arguments, Then it returns up to 20 of the caller's designs (id, title, thumbnail URL, edit URL, view URL, last-updated time) and, if more exist, a continuation token the caller can pass back to get the next page.
- **AC4**: Given a valid access token, When `canva_list_designs` is called with a search query that matches nothing, Then it returns an empty list — not an error, not a `not_found` code.
- **AC5**: Given a valid access token and a design id that exists and is visible to that account, When `canva_get_design` is called, Then it returns the design's metadata (id, title, page count, thumbnail, edit/view URL).
- **AC6**: Given a design id that does not exist, or exists but is not visible to the current token's account, When `canva_get_design` is called, Then it returns a structured `not_found` error — not a raw passthrough of Canva's 4xx body.
- **AC7**: Given a valid access token, When `canva_create_design` is called with a supported design type and a title, Then a new, empty design is created in the caller's Canva account and its id and edit URL are returned.
- **AC8**: Given a valid access token and an existing, visible design id, When `canva_export_design` is called with `format=pdf`, Then, within the tool's internal poll budget (see Tech design §7), it returns one or more download URLs for the exported file; if the export job is still running when the budget is exhausted, it returns the export job id instead of blocking, so the caller can poll `canva_get_export_status`.
- **AC9**: Given an export job id from AC8 that has not finished, When `canva_get_export_status` is called, Then it returns the job's current status and, once it reaches success, the download URL(s) from that job.
- **AC10**: Given a valid access token and a publicly reachable URL to an image or video, When `canva_upload_asset_from_url` is called, Then the asset is uploaded into the account's Uploads folder and its asset id is returned.
- **AC11**: Given a valid access token, When `canva_list_folder_items` is called with `folder_id` omitted (defaults to `root`), Then it returns the immediate contents of the account's top-level Projects folder (designs and sub-folders), paginated the same way as `canva_list_designs`.
- **AC12 (multi-tenant isolation)**: Given two different tenants, each with a different valid Canva access token, When each calls any Canva tool concurrently, Then each sees only the Canva account tied to its own token — the service must not cache, pool, or leak one request's token or response data into another request's context (SOP §3.3/§3.4: `ContextVar`, no globals/module singletons).
- **AC13 (resilience)**: Given the Canva API returns `429` or a `5xx`, When any tool calls it, Then the service retries with backoff within the single-call budget (<120s total, SOP §5) and, if it is still failing when the budget runs out, returns a structured `upstream_error` with `retryable: true` — it must not crash the request or hang past the budget.
- **AC14 (expired/revoked token)**: Given an access token that Canva has since revoked or that has expired, When any tool is called, Then Canva's `401` is surfaced as this service's own `401` (not treated as a transient/retryable error), so the platform knows to prompt the tenant to reconnect rather than silently retrying forever.

### Open questions

- [assumed / not blocking] **Does the platform's Connect-style OAuth flow for this tenant already exist, or does onboarding Canva require building a new "obtain and refresh an OAuth token on the tenant's behalf" piece elsewhere in the platform (outside this repo)?** This design assumes "yes, that piece already exists or will exist outside `canva-mcp`" — see "Decisions made by DEV01" below for why that is the only option consistent with the SOP's stateless/Header-only credential model, and Tech design §11 for the risk if that assumption is wrong. Not blocking: there is only one way to build a stateless, Header-credentialed MCP service regardless of the answer, so the assumption does not change what gets built in this repo; it only changes which other team has follow-up work. If the assumption is wrong, that surfaces at the `/api/vendor-register` step (dev/review leg) as a hard stop, not as a silently wrong connector.
- [not blocking] Exact OAuth scope names required per endpoint (`design:meta:read`, `asset:read`, `asset:write`, `folder:read`, `profile:read`, and whichever scope covers triggering an export/creating a design) are taken from Canva's authentication page's example list and resource-group documentation, not from the full OpenAPI spec (`https://www.canva.dev/sources/connect/api/latest/api.yml`) line by line. Default: the dev leg confirms the exact scope-to-endpoint mapping against the OpenAPI spec while building, and the app's registered scopes in the Canva Developer Portal are set to match. This cannot change the tool surface, only the scope list declared when the Canva app is registered, so it does not block design.
- [not blocking] Whether Canva enforces a documented rate limit was not stated in the fetched docs pages. Default: implement the generic backoff/retry behaviour required by SOP §5 regardless (connect/read timeouts, bounded retries on 429/5xx, respect `Retry-After` if present) — this does not depend on knowing the exact numeric limit.

## Tech design

### Conclusion

Build `canva-mcp` from scratch as a new Python/FastMCP service (SOP §9 recommended stack), implementing 9 tools across 4 Canva resource groups (Users, Designs, Exports, Assets, Folders) that wrap the public Canva Connect REST API. Every tool call forwards a single already-obtained Canva OAuth access token taken from a request Header straight through to Canva as a Bearer token; this repository does not implement the OAuth authorization/consent/refresh dance itself, because doing so would require persisting per-tenant state, which conflicts with the SOP's stateless/request-isolated service model (§5/§11 below explain why this is the only workable split and what the residual risk is).

### Where the current implementation lives

There is no current implementation. `MSPbotsAIFramework/canva-mcp@main` (`e828ad9`) contains only `README.md`. No other repository in `MSPbotsAIFramework` references Canva (verified org-wide, see Current state).

The closest same-shape reference inside the org is any other already-shipped single-vendor, Header-credentialed, FastMCP-based connector built under the same SOP (e.g. the pattern described throughout `vendor-mcp-development/SKILL.md` §A3/§A4) — there is no in-repo code to cite because none exists yet; the new service is built to match the SOP's structural requirements directly rather than copying a sibling repo (none was opened for this design; the SOP itself is the "spec to copy").

### Option analysis

| Option | Approach | Pros | Cons | Verdict |
|---|---|---|---|---|
| A. Thin stateless REST wrapper, token passed through from Header | MCP tools map 1:1-ish (grouped, not literal) onto Canva REST calls; access token forwarded as `Authorization: Bearer <token>` on every outbound call | Matches SOP's mandatory stateless/Header-credential model; no new persistent state in this repo; simplest to review and operate | Requires some other platform component to have already obtained a valid, fresh Canva OAuth token before the Header arrives here — this repo cannot self-refresh | **Chosen** |
| B. Service implements the OAuth Authorization Code + PKCE flow itself (redirect handling, code exchange, refresh-token storage) | Service owns the full OAuth lifecycle for each tenant | Fewer moving parts spread across teams | Needs persistent per-tenant token storage and a public redirect endpoint — directly violates SOP §1.3 "truly stateless" and §3.3 "request-level isolation, no shared state"; also not how any other connector on this platform is built | Rejected — breaks the platform's architecture, not a Canva-specific problem |
| C. Build nothing yet; return the ticket for a narrower scope decision | — | Avoids guessing which Canva capabilities matter most | The ticket's ask ("give AI live access to Canva") is unambiguous about wanting *a* working connector; nothing in it needs a product decision before building — this is an implementation-detail question (which resource groups make v1), not a requirements question | Rejected — not an Open-question-worthy fork; resolved by picking a reasonable v1 scope and listing the rest as non-goals |

### Decisions made by DEV01

(SOP §A4 requirement for a new vendor MCP's first version — every call made here with nobody to ask, and why.)

- **The OAuth Authorization Code + PKCE flow (user consent, redirect, code exchange, refresh) is explicitly out of scope for this repository.** `canva-mcp` only reads a Header-supplied access token and forwards it to Canva; it never performs the authorization dance itself. Why: Canva's auth model requires per-tenant, long-lived, refreshable state (refresh tokens, each single-use) and a public redirect callback. The SOP's non-negotiable tenets for every vendor MCP — "truly stateless" (§1.3), "credentials only from Header, never persisted" (§3.1), "request-level isolation, no shared state" (§3.3/§3.4) — are incompatible with a service that owns a token-refresh lifecycle. The only way to satisfy both "connect Canva" and "stay inside this architecture" is to put the OAuth lifecycle in whichever platform layer already handles it for other OAuth-style connectors, and have that layer supply this service with a currently-valid access token per request. Alternative considered: implement OAuth here anyway — rejected, see Option B above.
- **Credential Header name is `X-Canva-Access-Token`, not `X-Canva-Api-Key`.** Why: Canva has no static API key concept for the Connect API — every credential is an OAuth bearer token, so naming the Header "Api-Key" would be misleading to whoever configures it. Alternative: a generic `Authorization` Header — rejected, the SOP requires vendor-specific Header names (`X-<Vendor>-<Credential>`) so the gateway can route/log per-vendor without parsing a shared Header's contents.
- **9 tools, grouped by capability not by literal endpoint.** Why: Canva's Connect API has 10+ resource groups and 25+ endpoints; the SOP caps a service at ≤20 tools and explicitly says tools are "capabilities, not API endpoint mirrors" (§A4). Export and asset-upload are each collapsed into a create+poll pair (2 tools) instead of exposing the raw job-creation and job-status endpoints 1:1 with extra passthrough parameters; folder "get metadata" and "list items" are collapsed into the single `canva_list_folder_items` (folder metadata for a specific id can be read off the parent's listing — a standalone "get folder" tool wasn't judged worth a 10th tool slot for a connector this narrow). Alternative: expose closer to all ~15 read-oriented endpoints across every resource group — rejected as needlessly large for a v1 nobody has asked to go deeper on yet (see Non-goals).
- **Asset upload only supports "from a URL" in v1, not raw binary content.** Why: see Non-goals — MCP tool arguments are JSON; accepting file bytes means base64-encoding into a single call, which the SOP's token-economy rules push against, and the ticket's "AI gets access" framing fits an agent handing over a URL far better than raw bytes.
- **Default `limit` for list-style tools is 20, hard cap 50.** Why: SOP §A4 requires a default ≤50 and a hard cap ≤200, "never unbounded"; 20 was picked (rather than, say, 50) because Canva's own list payload per design includes a thumbnail URL and two link URLs, which adds up faster per-item than a typical lightweight record, so a smaller default keeps a typical response comfortably under the 20,000-character response cap even with the agent's own formatting overhead on top.
- **List/export/upload pagination and job-status fields are passed through largely as Canva returns them (`continuation` token, job `status` enum), not re-invented.** Why: SOP §A4 is about trimming token-expensive fields and limits, not about hiding a vendor's native cursor/job-status shape behind a bespoke one; re-inventing pagination semantics here would be the kind of unnecessary abstraction the "reuse before build" cleanup rule (Reuse & cleanup) argues against.

### Data & API contract

All tools call `https://api.canva.com/rest/v1` with `Authorization: Bearer <token-from-X-Canva-Access-Token-header>`. Request/response shapes below are this service's MCP tool contract, not Canva's raw REST shape (fields are trimmed per SOP §A4 token-economy rules); the Canva REST calls each tool makes internally are noted under "Canva call".

- **`canva_get_user_profile()`**
  Canva call: `GET /v1/users/me/profile` (falls back to `GET /v1/users/me`, which needs no scope, if `profile:read` was not granted — used as the "am I even connected" smoke-test tool).
  Response: `{"display_name": "...", "team_name": "..."}` (team_name omitted if not returned by Canva).
  Errors: `unauthorized` (missing/invalid/expired token).

- **`canva_list_designs(query?: str, ownership?: "owned"|"shared"|"any" = "any", limit?: int = 20, continuation?: str)`**
  Canva call: `GET /v1/designs?query=&ownership=&continuation=` (limit is enforced by this service truncating/paginating Canva's response, not forwarded as a Canva query param unless the OpenAPI spec confirms one exists — confirm at implementation time, Open question above).
  Response: `{"designs":[{"id","title","thumbnail_url","edit_url","view_url","updated_at"}], "continuation": "..." | null}`.
  Errors: `invalid_argument` (bad `ownership` value), `unauthorized`, `upstream_error`.

- **`canva_get_design(design_id: str)`**
  Canva call: `GET /v1/designs/{design_id}` + `GET /v1/designs/{design_id}/pages` (page count only).
  Response: `{"id","title","page_count","thumbnail_url","edit_url","view_url"}`.
  Errors: `not_found` (unknown id, or id not visible to this token — Canva's own 404 for both cases, passed through as one `not_found`, not distinguished, to avoid confirming resource existence across tenants), `unauthorized`.

- **`canva_create_design(design_type: str, title?: str)`**
  Canva call: `POST /v1/designs` with `{"design_type": {...}, "title": ...}`.
  Response: `{"id","edit_url"}`.
  Errors: `invalid_argument` (unsupported `design_type`), `unauthorized`.
  `destructiveHint: false`, `idempotentHint: false` (creates a new design every call), `readOnlyHint: false`.

- **`canva_export_design(design_id: str, format: "pdf"|"png"|"jpg"|"pptx"|"gif"|"mp4"|"csv" = "pdf", pages?: list[int])`**
  Canva call: `POST /v1/exports` with `{"design_id","format": {"type": format, ...}, "pages"}`, then this service polls `GET /v1/exports/{export_id}` internally (interval ~2s, bounded by the single-call <120s budget).
  Response (job finished within budget): `{"export_id","status":"success","urls":["https://...", ...]}`. Response (budget exhausted, job still running): `{"export_id","status":"in_progress"}` — caller follows up with `canva_get_export_status`.
  Errors: `invalid_argument` (format not supported for this design's type — e.g. multi-page non-Presentation designs can't export to `pptx`, per Canva's documented constraint), `not_found` (design_id), `unauthorized`, `upstream_error` (export job itself reports `failed`).

- **`canva_get_export_status(export_id: str)`**
  Canva call: `GET /v1/exports/{export_id}` (single read, no internal poll).
  Response: `{"export_id","status":"in_progress"|"success"|"failed","urls":[...] (only when success)}`.
  Errors: `not_found` (unknown export_id), `unauthorized`.

- **`canva_upload_asset_from_url(url: str, name?: str)`**
  Canva call: `POST /v1/asset-uploads` (URL-based job variant) with `{"url","name"}`, then this service polls the job's `GET` endpoint internally (same bounded-poll pattern as export).
  Response (finished within budget): `{"asset_id","name","thumbnail_url"}`. Response (budget exhausted): `{"job_id","status":"in_progress"}`.
  Errors: `invalid_argument` (unsupported mime type, or file exceeds Canva's documented size limits — images 50MB/SVG 3MB, videos 500MB), `upstream_error` (URL unreachable by Canva, job reports `failed`), `unauthorized`.
  `destructiveHint: false`, `idempotentHint: false`.

- **`canva_get_asset(asset_id: str)`**
  Canva call: `GET /v1/assets/{asset_id}`.
  Response: `{"id","name","thumbnail_url","type"}`.
  Errors: `not_found`, `unauthorized`.

- **`canva_list_folder_items(folder_id?: str = "root", item_types?: list["design"|"folder"|"image"], limit?: int = 20, continuation?: str)`**
  Canva call: `GET /v1/folders/{folder_id}/items?item_types=&continuation=`. `folder_id` accepts Canva's two reserved ids (`root`, `uploads`) as well as a real folder id.
  Response: `{"items":[{"id","type","title or name","thumbnail_url"}], "continuation": "..." | null}`.
  Errors: `not_found` (unknown folder id), `invalid_argument` (bad `item_types` value), `unauthorized`.

**DB**: none — this service is stateless and has no database (SOP §1.3/§3.4; consistent with every tool above being a pure pass-through to Canva).

**Events/messages**: none — no queue, no webhook consumption or emission in v1 (Non-goals).

**Backward compatibility**: not applicable yet — this is a first version, there is no prior tool contract to stay compatible with. Once registered, future changes to these 9 tools follow the SOP's breaking-vs-compatible change rules (§B3).

### Key flow / sequence

Primary path — list, inspect, export:

```
Agent -> Gateway -> canva-mcp: tools/call canva_list_designs {query:"Q4 deck"}
canva-mcp -> Canva: GET /v1/designs?query=Q4+deck   (Authorization: Bearer <token from Header>)
Canva -> canva-mcp: 200 {items:[...]}
canva-mcp -> Agent: {"designs":[...], "continuation": null}

Agent -> Gateway -> canva-mcp: tools/call canva_export_design {design_id:"DAx...", format:"pdf"}
canva-mcp -> Canva: POST /v1/exports {design_id, format:{type:"pdf"}}
Canva -> canva-mcp: 200 {export_id, status:"in_progress"}
canva-mcp -> Canva: GET /v1/exports/{export_id}   (repeated, bounded, ~2s interval)
Canva -> canva-mcp: 200 {status:"success", urls:[...]}
canva-mcp -> Agent: {"export_id","status":"success","urls":[...]}
```

Credential/isolation path (every call):

```
Gateway -> canva-mcp: POST /mcp   Header: X-Canva-Access-Token: <tenant's token>
middleware: token = Header value; ContextVar.set(token)
tool handler: reads token via ContextVar (never a parameter, never a global)
client.py: Authorization: Bearer <token> on the single outbound Canva call
finally: ContextVar.reset()   # runs even on error, so nothing leaks to the next request
```

### Non-functional

- **Idempotency & concurrency**: all tools except `canva_create_design`, `canva_export_design`, `canva_upload_asset_from_url` are pure reads (`readOnlyHint: true`), naturally idempotent. The three write/creating tools are explicitly `idempotentHint: false` — calling them twice creates two designs/exports/assets; this is accepted for v1 (the SOP doesn't require idempotency keys for connectors unless the ticket calls for it) and documented in each tool's description so an agent doesn't assume a safe retry.
- **Performance**: no local data store, so the only "data volume" concern is list-endpoint response size — bounded by `limit`≤50 default 20 and the 20,000-character response cap (SOP §A4). Export and asset-upload are the only slow paths (Canva's own async jobs); bounded internally per AC8/AC10 rather than blocking the MCP call indefinitely.
- **Security**: credentials never touch disk, env vars, or logs (SOP §3.1); every outbound Canva call uses exactly the Header-supplied token, never a service-wide default; `gitleaks detect` run before any commit that could contain a real token (local testing only, never committed); README's Header table documents exactly what scope each Header unlocks so whoever configures the connection knows the blast radius of the token they're issuing.
- **Multi-tenant isolation**: `ContextVar`-scoped token (SOP §3.3/§3.4), no module-level/global state, no caching of any tenant's designs/assets/folders across requests — AC12 is the acceptance test for this; `tests/test_middleware.py` asserts it at the unit level with two concurrent requests.
- **Observability**: structured logs per request (method, tool name, Canva HTTP status, latency, retryable flag) — never the token itself, never full response bodies (could contain tenant content). `/health` is a pure liveness probe (no outbound Canva call), so health-check noise never counts against Canva's own rate limits.

### Rollout & rollback

- **Rollout**: single repo, no cross-repo dependency (`Track: vendor-mcp`, `release order: n/a` — see ticket stub). First version goes straight to `main` (SOP §A2: "new repo, nobody knows about it yet, first version can commit directly"), then registered via `/api/vendor-register` (new vendor, not yet known to the INT gateway) rather than `/api/deploy-int`. No feature flag — this is a brand-new connector with no existing traffic to gate.
- **Rollback**: registration only exists on INT; if `/api/vendor-register` or the post-register health check fails, nothing is live and there is nothing to roll back — the review leg reports the failure and the ticket returns to a dev round. After a successful registration, a broken subsequent tool change would be rolled back the normal vendor-mcp way: revert the breaking commit on `main`, re-publish via `/api/deploy-int` (not `vendor-register`, the vendor already exists by then).

- **Unit (auto), no real account needed**: `tests/test_tools.py` — `tools/list` snapshot (AC1); empty-result pass-through when Canva returns no matches (AC4); `not_found` mapping on a mocked 404 (AC6); backoff-then-succeed and budget-exhausted-`upstream_error` on mocked 429/5xx (AC13); immediate non-retried `unauthorized` on a mocked 401 (AC14). `tests/test_middleware.py` — missing-Header 401 naming the Header (AC2); `ContextVar` isolation across two concurrent fake requests with different tokens, asserting neither sees the other's token (AC12).
- **Integration, no real account needed**: local server + placeholder credential Header (well-formed but fake token) — `initialize → tools/list` returns 9 tools; missing Header → 401; `/health` → 200 without calling Canva (SOP §A5).
- **Needs a real Canva account** (flagged, not blocking per SOP "no test account is not a blocker"): AC3, AC5, AC7, AC8, AC9, AC10, AC11 — the cases that only mean something against a real Canva account's real designs/assets/folders (listing real designs, reading a real design's metadata, creating a design that then actually shows up, a real export job finishing, a real asset upload, real folder contents). - **Regression face**: none in this repo (no prior version exists). Future changes must keep `tests/test_tools.py`'s `tools/list` snapshot in sync (SOP §B3) so a breaking tool-signature change is caught by CI, not by a downstream tenant's agent breaking silently.

### Risks & dependencies

- **Risk**: Canva's OAuth bearer-token-as-Header model may not be accepted cleanly by `/api/vendor-register`'s `credential_fields` schema if the registration pipeline treats "OAuth" as categorically unsupported rather than looking at the Header's declared type (string/password). Mitigation: declare `X-Canva-Access-Token` as a plain `password`-type field (mechanically identical to a static API key from the registration API's point of view) per "Decisions made by DEV01"; if registration still rejects it as "needs OAuth special handling", the vendor-mcp-development SKILL's own escalation path applies (blocked, routed to manual registration) — this is a dev/review-leg risk to carry forward, not a design blocker, since the code and contract are correct regardless of which registration path is used.
- **Risk**: exact Canva scope-to-endpoint mapping and any undocumented rate limit were not available in the fetched documentation pages (Open questions above). Mitigation: confirm against the published OpenAPI spec during implementation; no design rework needed either way — the tool contracts in §5 do not depend on knowing the limit, only on having *some* bounded retry/backoff (already specified in §7).
- **Dependency**: none on another ClickUp ticket or another repo — `canva-mcp` is a standalone MCP repo (`Track: vendor-mcp`, single repo).
- **Dependency**: a real Canva developer account + registered app (client ID/secret, redirect URL, scopes) is needed to obtain a real access token for integration testing and for whatever platform component ends up performing the OAuth exchange. Per SOP, the absence of this during the design round is not a blocker; per "no test account" handling, it is also not a blocker during dev — the relevant test cases are flagged "needs a real vendor account" (`.ac.json`) rather than marked failing.
